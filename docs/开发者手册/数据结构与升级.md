# 数据结构与升级

> 本文说明数据库表、字段和升级方法。建表定义见 [schema.sql](../../src/main/resources/db/schema.sql)，玩法见[玩法与范围](../MVP/玩法与范围.md)，计算方法见[规则与数值](../MVP/规则与数值.md)。

## 一、保存约定

玩家与 NPC 共用数据结构，各自保存钱包、背包、领域档案、对话和考试记录。程序分工见[接口与方法](./接口与方法.md#一程序分工)。

游戏先后顺序使用 `total_turn_number`，现实创建时间只记在存档上。金额、阅读进度和考试分数使用整数，学识允许小数；数据库中的 AI 字段以 `ai_` 开头，Java 对应使用 `aiText` 等小驼峰名称。

## 二、总体关系

当前新库共13张表：

```text
region ← parent_id 自关联
  ↑ 出生地、所在地
game_save
  ├─ family_background
  ├─ game_character（玩家与NPC）
  │   ├─ career_profile_shusheng
  │   ├─ character_equipment → equipment_definition
  │   ├─ character_book_progress → book_definition
  │   ├─ exam_record
  │   └─ memory_record → event_record
  ├─ event_record（人生节点与请求结果记录）
  └─ dialogue_record（双方均引用本存档人物）

equipment_definition ← book_definition 一对一扩展
```

装备和地区定义跨存档共用。人物、领域档案、背包、阅读、事件、记忆、考试和对话属于某一存档。

## 三、地区关系

| 字段 | 含义 |
|---|---|
| `id` | 地区ID |
| `parent_id` | 唯一的直接上级ID，根节点为空 |
| `region_name` | 地区显示名称 |
| `enabled` | 是否启用 |

地区关系由 `parent_id` 表达，不另存编码、等级或排序。`Region` 对应 `region` 表，首版节点为：

```text
广东省
├─ 广州
│  ├─ 番禺
│  ├─ 南海
│  └─ 顺德
└─ 惠州
   ├─ 博罗
   └─ 海丰
```

首版地区 ID 使用字符串 `1`～`8`，不补前导零：广东省为 `1`，广州为 `2`，惠州为 `3`，五个县依次为 `4`～`8`。`parent_id` 和人物的地区引用使用相同 ID。

出生地查询使用初始化数据中的惠州 ID `3`，返回启用的直属子节点，不指定显示顺序；管辖关系可沿父节点向上查找。

## 四、存档、人物与初始家庭背景

### game_save

| 字段 | 含义 |
|---|---|
| `id`、`created_at` | 存档ID和现实创建时间 |
| `status`、`growth_stage` | 当前流程状态与成长阶段 |
| `birth_year`、`age` | 主角出生年和当前年龄 |
| `current_year`、`current_month`、`turn_in_month` | 当前世界日历 |
| `total_turn_number` | 已经过的普通及强制休养回合数 |

存档只有一条共享时间线。NPC 通过通用行动接口消耗回合时，也推进该时间线；`age` 始终是玩家年龄，NPC 年龄另按自己的生日年份计算。节点考试的归属与存档阶段规则见[考试](#八考试exam_record)；尚无独立的后台 NPC 调度或个人考试日历。

### game_character

| 字段组 | 含义 |
|---|---|
| `id`、`save_id`、`name` | 人物身份及所属存档 |
| `type` | 控制类型，1为玩家、0为NPC；动作共用入口，玩家节点考试以此区分归属 |
| `npc_code` | 本局固定NPC对应的资源编码；玩家为空 |
| `birth_region_id`、`current_region_id` | 出生地与当前所在地 |
| `character_zhili/daode/zhengzhi/jiaoji/tineng` | 五项通用属性 |
| `character_jiankang`、`character_pilao` | 当前健康、疲劳 |
| `wallet` | 当前可支配资金，整数文数 |
| `sick_turns_remaining` | 尚未完成的强制休养回合 |
| `official_position`、`official_rank`、`degree` | 存档列表需要的官职、级别、学位/功名展示字段 |
| `titles_json` | 可同时保有的称号数组，初始为 [] |
| `birthday`、`personality_summary`、`current_state` | 生日、稳定性格及当前状态摘要 |
| `available_stage_code_json`、`enabled` | 可参与阶段与启用状态 |

`(save_id, npc_code)` 唯一，同一 NPC 在本局只生成一次。人物钱包与家庭财富分别保存，初值见[开局与时间](../MVP/规则与数值.md#二开局与时间)。

身份字段用于显示，不自动授予官职、学位或权限。[官职与爵位](../后续设计/官职与爵位.md)另有后续方案，MVP 不实现。

### family_background

每局一条，`save_id` 唯一，描述玩家初始家庭而不是本局所有 NPC 的共同背景。`initial_wealth` 保存初始家庭财富，`background_summary` 在开局时保存固定背景，独立调用童年背景接口成功后保存六岁入学前的叙事；数值见开局规则，交易不修改本表。

背景是否已生成由 `event_record` 中本存档唯一的 `CHILDHOOD_BACKGROUND/{saveId}` 请求标记确认，事件编码为 `CHILDHOOD_BACKGROUND`、`life_milestone=false`、发生回合为 0；结果只记录家庭背景 ID 和生成完成标记，不重复保存正文。叙事和标记在同一事务提交，重复调用及读档使用原背景；不以正文长度或是否等于默认文字推断生成状态。

## 五、领域档案：career_profile_shusheng

一位人物一份书生档案，`character_id` 唯一并直接引用人物。其他领域将使用各自的档案表，彼此不互斥。

| 字段 | 含义 |
|---|---|
| `id`、`character_id` | 档案ID与所属人物 |
| `unlock_turn_number` | 首次建立档案的回合 |
| `last_active_turn_number` | 最近参与该领域结算的回合，可为空 |
| `ability_shizi/jingyi/wenzhang/celun/wenxue` | 识字、经义、文章、策论、文学能力 |

读书、练习、考试和 AI 属性结算更新最后活跃回合，休息不更新。能力初值与范围见[规则与数值](../MVP/规则与数值.md)。

## 六、装备、书籍与阅读

### equipment_definition / book_definition

通用装备保存 `equipment_code`、名称、类型、品质、整数价格、`supplier_npc_code` 和介绍。`rarity_code` 是所有装备共用的五档品质：COMMON白、UNCOMMON绿、RARE蓝、EPIC紫、LEGENDARY金；名称和颜色由代码推导，不另加字段。供应编码对应NPC原型，由业务层映射到当前存档中的实际人物，不跨存档引用NPC主键。

书籍以 `equipment_id` 一对一扩展装备，保存领域编码、阅读条件JSON、`player_reading_enabled`、五项能力权重、疲劳、`total_knowledge` 和单一 `knowledge_summary`。`player_reading_enabled` 默认0，允许以身入局的科举类书籍设为1。完成进度统一为100、基础阅读速度统一为每回合13点，由 `GameRuleConstant` 维护，不再存储逐书难度、总进度和基础速度。

`total_knowledge` 为读满学识，`knowledge_summary` 为完整内容介绍；计算方法见[阅读与学识](../MVP/规则与数值.md#四阅读与学识)。

新开局或调用补内容接口时，只插入缺失定义，不覆盖已有记录。修改 JSON 不会自动更新数据库；首次初始化时的并发冲突见[待办事项](../MVP/待办事项.md#四后续设计和已知限制)。

### character_equipment

| 字段 | 含义 |
|---|---|
| `save_id`、`character_id`、`equipment_id` | 存档、持有人、装备定义 |
| `quantity` | 本次获取数量，正整数 |
| `acquired_turn_number` | 本次实际入包回合 |
| `status` | 当前使用 OWNED 表示持有 |
| `ai_text` | 可选来源叙事，Java为 aiText |

每次获取产生一条记录，同种装备允许多条、多件，背包按装备定义合计数量。新库没有“人物＋装备”的唯一限制，也没有借阅或到期字段；升级库可能保留旧到期列，但当前业务不再使用。

免费领取同样需要建立记录；购买时，扣款、收款、入包和请求结果在同一事务保存。

### character_book_progress

`(character_id, equipment_id)` 唯一，保存 `current_progress`、`total_read_turn_number`、`completed` 和 `last_read_turn_number`。无记录按零进度展示，首次实际读书才创建。

持有数量与阅读进度相互独立：同一种书多本不重复加学识，失去物品不删除已学进度。总学识从所有阅读记录计算，不在人物表再存一份可变汇总。

## 七、事件、对话与记忆

### event_record

同表区分两种记录：

| 类型 | 特征与用途 |
|---|---|
| 人生节点 | `life_milestone=true`，用于展示首次读满、考试和重要自由行动；`request_id` 可为空 |
| 请求结果 | `life_milestone=false`，保存固定行动、获取、自由行动、对话的原请求与已执行结果 |

`(save_id, request_id)` 唯一。`request_payload_json` 保存原参数，`settlement_result_json` 保存响应及阅读骰点；同一编号、相同参数重传时返回原结果，换参数则拒绝。新操作使用新编号。

`event_code`、`event_summary`、`related_character_id_json`、`occurred_turn_number` 描述已发生事实。人生节点列表只读取标记为真的记录，不展示普通请求结果。

以身入局读书复用此表：`BOOK_PLAYER_QUESTION` 保存题目、书籍、玩家及出题回合；`BOOK_PLAYER_ANSWER` 保存玩家原文、评分与实际结算。出题请求编号由玩家、书籍定义ID和回合组成，交卷编号由该题编号推导，利用既有唯一约束和存档锁保证同一道题只结算一次。两个操作都不标记为人生节点，首次读满仍单独记录 `BOOK_MASTERED`。

### dialogue_record

| 字段 | 含义 |
|---|---|
| `id`、`save_id` | 整场对话与所属存档 |
| `actor_id`、`counterpart_id` | 本存档内的发起者和对话对象 |
| `scene_code`、`started_turn_number` | 场景与开始回合 |
| `version` | 已成功完成的对话轮数，一次行动者输入与对方回应算一轮，最多 5 轮 |
| `ended` | 是否已经结束并完成整场属性结算 |
| `messages_json` | 对话原文、手动结束标记及已执行交易 |

普通往返可完成本轮明确的交易，但不结算属性；手动或模型结束时只结算一次属性。结束标志、历史、交易、属性和结果记录在同一短事务提交。模型请求在事务外执行。

模型通过 `endDialogue=true` 结束，可按语义提前结束，第五轮必须结束。第五轮仍返回 `false` 的结果被拒绝，不增加版本或保存本轮结算；此前成功轮次保持原样。

### memory_record

本表只保存索引和关联，不保存记忆正文；`(owner_character_id, source_event_id)` 唯一，同一事件可以按实际参与人物分别生成记忆。

| 字段 | 含义 |
|---|---|
| `id`、`save_id` | 记忆 ID 与所属存档，用于定位 JSON 文件 |
| `owner_character_id` | 记忆所属人物，用于将检索限定为该人物自己的经历 |
| `source_event_id` | 已提交的来源事件 ID |
| `related_character_id_json` | 事件涉及的人物 ID 数组 |
| `scene_code` | 来源中能够确认的场景编码，可为空 |
| `related_equipment_code_json` | 来源中能够确认的相关物品编码数组，无物品时为 `[]`，不可为空 |
| `occurred_turn_number` | 事件发生回合 |

正文存于应用工作目录下的 `memory/<saveId>/<memoryId>.json`，UTF-8 编码，结构如下：

```json
{
  "version": 1,
  "id": "记忆 ID",
  "saveId": "存档 ID",
  "ownerCharacterId": "所属人物 ID",
  "sourceEventId": "来源事件 ID",
  "occurredTurnNumber": 12,
  "summary": "根据已确认经历生成的压缩记忆"
}
```

`summary` 不超过 1000 个 Unicode 字符；数据库索引与文件身份字段须一致。检索返回 `[{memoryId, sourceEventId, turnNumber, summary}]`，最多 8 条，序列化后的整体 JSON 不超过 5000 个 Unicode 字符，优先与当前对象相关的近期记忆。

结束对话和人生节点提交后，同步生成参与者摘要并在独立短事务中保存索引，模型调用不持有原业务事务；这不是后台任务。摘要失败不回滚已完成事件，后续相关检索每次最多补 2 条，单条失败后等待 60 秒再尝试。只有已确认发言、交易和真实参与关系可以进入记忆，内部 `AI_ACTION` 不单独记忆。

## 八、考试：exam_record

`(character_id, exam_type)` 唯一，每人物每种考试一份；类型为 EXAM_MENGXUE、EXAM_JINGYI、EXAM_PRE_COUNTY、EXAM_XIANSHI。

当前四个年龄节点只自动创建玩家考试，与最后行动的是玩家还是 NPC 无关。数据结构及计分入口仍可承载 NPC 成绩，但只有玩家考试结算可以恢复求学或结束存档。

准备时固定题目、通过线、基础能力分B、身体偏移R、`dice_roll`、`luck_offset`、`knowledge_total` 和发生回合。`knowledge_total` 使用 DECIMAL(16,4)，其他上述分数和骰点为整数。

结算时保存参与方式（`AUTO` 或 `PLAYER`）、最终整数分和通过状态。两种方式均使用已保存的 B/R 及骰点，不重新投骰；同一考试只结算一次，不能更换方式或答案。玩家提交的 `requestId`、原始参数和完整响应保存在 `event_record`，以 `(save_id, request_id)` 防重；考试表的 `request_id` 仍为保留字段，本轮无需修改表结构。

`ai_thought_bubble` 保存单场考试的思路缓存；`player_input` 保存玩家原文；`ai_player_content_modifier` 保存程序限幅并取整后的内容修正（玩家为 -10～10，系统代行为 0）；`ai_answer_text` 仅保存系统代行答卷；`ai_content` 保存玩家内容评价与结果总结，或系统代行结果总结。成绩、作答方式、答案及展示文字与存档阶段在一个事务中保存。

模型调用期间不持有数据库事务，保存前重新取得存档锁并核对考试快照与状态。AI 失败不会写入部分结果；历史已完成记录继续使用原成绩和原文字，不重新生成。

## 九、数据关联与删除

地区以 ID 标识，装备编码唯一；人物与存档的复合外键保证记录属于同一存档。数据库删除存档会连带删除本局人物、领域档案、背包、进度、事件、记忆索引、考试和对话，但外部记忆 JSON 不受数据库级联控制，维护时须按存档核对。仍被人物引用的地区、仍被存档使用的装备不能直接删除。

完整任职、关系数值、世界人口、县试后成长数据及[随机种子](../后续设计/随机种子.md)不在当前建模范围内。

## 十、数据库初始化与维护

### 本机共享数据库与缓存

本机只运行一组 `local` 服务：`mysql` 使用 `127.0.0.1:3306`，`redis` 使用 `127.0.0.1:6379`。各项目按数据库名区分数据，MVP 的 JDBC 地址统一为 `localhost:3306/mvp`；[schema.sql](../../src/main/resources/db/schema.sql) 只负责创建 `mvp` 库及其表，不启动独立 MySQL。

共享服务的唯一配置维护在本仓库根目录 [compose.yaml](../../compose.yaml)。记录助手项目的 Compose 入口通过 `include` 引用这份配置，并使用同一个 `local` 项目名；从任一入口启动都会管理同一组容器。MySQL 和 Redis 继续使用原有持久化数据卷，卷名保留历史名称，避免切换到空数据卷。3307 的原 MVP 数据已迁入共享实例，两个项目不再各建一套 MySQL/Redis。

### 初始化与正式定义

新库执行 [schema.sql](../../src/main/resources/db/schema.sql)，创建当前 13 张表、约束和地区基础数据。地区使用字符串 `1`～`8`；阅读表使用当前字段与约束，具体定义见第三、六节。`CREATE TABLE IF NOT EXISTS` 不会修改已有表，已有库需要调整时应先核对实际结构和数据。

内置书籍的正式定义保存在 [book.json](../../src/main/resources/game/book.json)：九本科举书允许以身入局，《GPT-1的权重》关闭。首次开局会将缺失定义写入数据库；仅执行 schema 后，书籍表为空是正常状态。

### 已有数据维护

已有存档可调用 `POST /api/save/{saveId}/content` 补齐缺失 NPC 和教材定义；不会覆盖已有定义或自动发书。修改 JSON 不会自动更新数据库中的已有记录，已有定义需要按实际差异单独调整。

SQL 文件使用 UTF-8，连接使用 utf8mb4，schema 显式执行 `SET NAMES utf8mb4`。错误的连接字符集会写入乱码，改表字符集不能修复已经写坏的内容。MySQL DDL 会自动提交，执行前须核对当前结构。

本机记忆表已切换为上述 8 个索引与关联字段；调整前已确认记忆表为空，无需迁移历史正文，调整后已核对字段结构。此项数据库检查不代表新增业务接口或模型调用已经运行验收。

新记忆正文写入 `memory` 运行目录，迁移运行位置或维护存档时须同时保留数据库索引与对应 JSON。其他旧库若仍有 `ai_memory_summary`，先检查是否已有记忆；有记录时必须先转存对应 JSON 并核对身份字段与正文，再移除旧正文列，不可直接丢弃。正式结构只保留索引和关联，维护过程不保留永久升级脚本。
